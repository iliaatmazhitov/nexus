# Логирование Nexus

Приложение использует `log/slog` и пишет логи в stdout. Access log — это
итоговая запись об HTTP-запросе: маршрут, статус, длительность и сведения об ошибке.
Имена полей записываются в `snake_case`. Имена, типы и единицы измерения полей
задают общую схему для поиска, графиков и алертов.

## Формат и уровень

| `APP_ENV` | Формат |
| --- | --- |
| Не задан или равен `dev` | Текстовый, `slog.TextHandler` |
| Любое другое значение | JSON, `slog.JSONHandler` |

Одна JSON-запись занимает одну строку. По умолчанию выводятся записи начиная
с уровня `Info`. Для вывода `Debug` логгеру задают
`HandlerOptions.Level = slog.LevelDebug`.

## Общие поля

`service`, `env` и `version` добавляются к логгеру при запуске приложения.

| Поле | Тип в JSON | Значение |
| --- | --- | --- |
| `time` | string | Время события в формате RFC 3339 |
| `level` | string | Уровень записи: `DEBUG`, `INFO`, `WARN`, `ERROR` |
| `msg` | string | Название события, например `http request` |
| `service` | string | Имя сервиса: `nexus` |
| `env` | string | Значение `APP_ENV`, по умолчанию `dev` |
| `version` | string | Версия, переданная при сборке, по умолчанию `dev` |

Для передачи Git-коммита в `version` выполните из корня репозитория:

```bash
commit=$(git rev-parse --short HEAD)
cd backend
go build -ldflags "-X main.version=$commit" -o bin/nexus ./cmd/server
APP_ENV=prod ./bin/nexus
```

Переданное значение появится в поле `version`, в том числе в записи `server started`.

## HTTP-запросы

`AccessLog` формирует запись с `msg = "http request"` после выполнения обработчика.
К общим полям добавляются:

| Поле | Тип в JSON | Значение |
| --- | --- | --- |
| `request_id` | string | Идентификатор запроса из `middleware.RequestID` |
| `client_ip` | string | IP клиента из контекста запроса |
| `method` | string | HTTP-метод |
| `path` | string | Путь запроса без query-параметров |
| `route` | string | Полный шаблон маршрута, например `/api/v1/channels/{id}`; при отсутствии шаблона — `UNMATCHED` |
| `status` | number, целое | HTTP-статус; если обработчик ничего не записал — `200` |
| `duration_ms` | number | Длительность обработки в миллисекундах, включая дробную часть |
| `bytes` | number, целое | Размер записанного тела ответа в байтах, без заголовков |

Порядок middleware в роутере:

```go
r.Use(
    middleware.RequestID,
    middleware.ClientIPFromRemoteAddr,
    httpx.AccessLog(d.Logger),
    httpx.Recoverer,
)
```

`ClientIPFromRemoteAddr` берёт IP из адреса соединения. Заголовки
`X-Forwarded-For` и `X-Real-IP` на это значение не влияют.

Шаблон `route` читается после обработки запроса, когда Chi определил маршрут.
Для группировки запросов подходят `route` и `status`. Поля `path` и `request_id`
используются для поиска отдельных запросов.

## Ошибки

Обработчик передаёт сведения об ошибке через `SetRequestError`:

```go
httpx.SetRequestError(r.Context(), "not_found", nil)
httpx.WriteError(r.Context(), w, http.StatusNotFound, "not_found", "route not found")
```

`SetRequestError` заполняет состояние текущего запроса, созданное `AccessLog`.
После завершения обработчика middleware добавляет эти сведения в лог:

| Поле | Тип в JSON | Когда добавляется |
| --- | --- | --- |
| `error_code` | string | Если сохранён непустой код ошибки |
| `error` | string | Если статус — 5xx и передана причина типа `error`; записывается `err.Error()` |

Для передачи ошибки используйте `r.Context()`. Без состояния запроса
`SetRequestError` ничего не делает. Состояние создаётся отдельно для каждого
запроса и заполняется синхронно во время обработки.

`WriteError` отправляет JSON-ответ клиенту. Код для access log обработчик
сохраняет отдельным вызовом `SetRequestError`. Внутренняя причина ошибки
передаётся в лог, а клиенту отправляется безопасное сообщение.

При ошибке сериализации `WriteJSON` сам сохраняет код `internal` и причину,
затем отправляет HTTP 500 с сообщением `internal error`.

### Паники

`httpx.Recoverer` перехватывает панику, сохраняет код `internal` и её причину,
затем вызывает `WriteHeader(500)`. После этого `AccessLog` записывает результат.
Причина паники не отправляется клиенту.

`http.ErrAbortHandler` передаётся дальше: это сигнал пакету `net/http` оборвать
ответ. Уже отправленный HTTP-статус изменить нельзя; access log сохраняет
фактический статус ответа.

Пример записи об ошибке сервера:

```json
{"time":"2026-11-19T14:00:00Z","level":"ERROR","msg":"http request","service":"nexus","env":"prod","version":"997ec60","request_id":"example-request-42","client_ip":"192.0.2.10","method":"GET","path":"/api/v1/channels/42","route":"/api/v1/channels/{id}","status":500,"duration_ms":12.4,"bytes":0,"error_code":"internal","error":"storage unavailable"}
```

В отдельных событиях `encode response`, `write response` и `service failed`
причина записывается в поле `err`. В access log для неё используется поле `error`.

## Уровни записей

| Уровень | События |
| --- | --- |
| `Debug` | Запросы к `/livez` и `/readyz`, ошибки записи тела ответа |
| `Info` | Запуск и остановка сервиса, обычные HTTP-запросы, включая 4xx |
| `Warn` | Восстановимые нештатные ситуации, требующие внимания |
| `Error` | Ответы 5xx, кроме health-проб; ошибки сериализации и работы сервиса |

Путь health-пробы проверяется раньше статуса. Поэтому `/readyz` со статусом
503 тоже записывается на уровне `Debug`. При стандартном уровне `Info`
записи health-проб не выводятся.

В событиях запуска и остановки используются дополнительные поля:
`addr` — адрес сервера, `drain` — время ожидания перед остановкой
(в JSON — число наносекунд).

## Чувствительные данные

В логи не записываются пароли, токены, содержимое `Authorization` и `Cookie`,
query-параметры, тела запросов и ответов, тексты сообщений и содержимое файлов.
При передаче причины ошибки убедитесь, что её текст не содержит секретов.
Секреты также не должны находиться в сегментах URL, поскольку путь попадает в лог.
